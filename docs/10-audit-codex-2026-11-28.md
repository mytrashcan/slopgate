## Codex 의 커버리지 판정 — "가장 조용히 깨질 게이트는 `cron_lint.py`"

Codex가 브리프 마지막 항목으로 낸 판정이다(내가 물은 것이고, 답이 왔다):

> `cron_lint.py` is the gate most likely to break silently in production. It misses disabled tools
> inherited from profile settings, ignores legacy skill attachments, and accepts archived skills that
> Hermes cannot load. Routine configuration and skill changes can therefore break scheduled jobs while
> lint stays green.

근거 3건은 F3·F6·F16 — **셋 다 고쳤다.** 그런데 이 판정 자체가 중요한 이유는
`cron_lint` 가 **실행 시점에만 드러나는 실패**(크론이 매 틱 조용히 실패)를 다루기 때문이다.
다른 게이트는 파일을 잘못 읽어서 틀리지만, `cron_lint` 는 **틀려도 초록**이고 대가는 나중에
스케줄된 잡이 아무것도 안 할 때 치른다.

그래서 이 게이트는 앞으로도 **설정·스킬 변경 때마다** 확인 대상이다. 세 축이 서로 다른 곳에서
데이터를 가져온다는 점이 구조적 위험이다:
① `jobs.json` (잡 정의) ② `~/.hermes/config.yaml` (상속 toolset) ③ `~/.hermes/skills/` (첨부 본문).
셋 중 하나만 바뀌어도 판정이 조용히 어긋난다.

1. **변이 실험은 true positive만 본다 — false negative와 이상 입력은 다른 브리프가 필요하다.**
   내 1차 감사는 "게이트가 우는가"를 봤고, Codex는 "게이트가 언제 조용한가"와
   "이상 입력에서 어떻게 죽는가"를 봤다. 같은 코드, 다른 질문, 14건이 추가로 나왔다.

   "Codex가 그럴듯하게 쓴 것"과 "실제 결함"을 구분할 수 있었다.
3. **`except` 에서 0/None 으로 삼키는 것은 게이트를 뒤집는 일이다.** RT006의 존재 이유가

   일자 정규식 그룹 순서 — 셋 다 "지금은 맞는" 값이었다.
