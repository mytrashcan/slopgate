# 방학 전에 정할 것

각 항목은 지금 결정하지 않아도 게이트가 돌아간다. 다만 방학 1단계를 시작할 때 답이 없으면
작업이 두 갈래로 갈라지므로, 시작 전에 정한다. 내 의견을 먼저 적어 두었다.

## Q1. 스킬 description 길이 기준

- **사실**: `skill_manage(create)`는 60자 근처에서 거부한다(API 제약). 파일에 직접 쓴 설명은 120자든 500자든 동작한다(비용만 든다).
- **선택지**: (a) 60자 통일 — 새 스킬은 API로만 만들게 되어 일관됨. 기존 스킬을 전부 고쳐야 함. (b) 120자 권고 + 비용 관점 경고 — 지금 상태. (c) 판단 없이 인덱스 총량만 관리.
- **내 의견**: (c) + 120자 경고 유지. 개별 길이보다 총량이 실제 비용이다. 수백 개를 손으로 줄이는 비용이 이득보다 크다. (2026-11-26 결정: **c로 확정**, 배치 1에서 119건에 트리거 접두만 추가하고 길이는 손대지 않았다.)

## Q2. 스킬 인덱스 예산

- **사실**: 60자 클립 기준 99,617자 ≈ 25k 토큰/세션(원본 설명 251,626자). 세션 수명이 길수록 이 비용은 한 번만 나가지만, 새 세션마다 반복된다. `SKL020`이 60,000자에서 경고한다.
- **선택지**: (a) 60,000자 — 스킬을 절반으로 줄여야 함(과감). (b) 80,000자 — 30% 축소, 현실적. (c) 예산 없이 관찰만.
- **내 의견**: (b). 자동 생성된 보안 스킬 묶음(analyzing-*·detecting-* 계열)은 실제로 거의 로드되지 않으므로, `description`을 짧게 줄이는 것만으로도 큰 폭 줄어든다. 삭제보다 안전하다.

## Q3. `.archive/` 129건 처리

- **선택지**: (a) 전부 삭제 — 되돌릴 수 없음(git에 없음). (b) 살릴 것만 복구, 나머지 tar로 보관. (c) 그대로 둔다.
- **내 의견**: (b). 삭제 전에 이름·설명만 뽑아 `docs/archive-index.md`로 남기면 나중에 "그 스킬 있었는데"를 막을 수 있다.

## Q4. 게이트를 언제 돌릴 것인가 — **해결됨 (c)**

2026-11-26: 일일 크론(`slopgate 일일 위생 게이트`, no_agent, 09:00, 토큰 0, 새 위반만 알림) + CI(`gates.yml`)로 확정.

- **선택지**: (a) 손으로만 — 가장 싸지만 잊는다. (b) PR 생성 전 체크리스트에 넣는다 — 강제력 약함. (c) 주 1회 크론 + PR 전 실행 — 균형. (d) git pre-commit 훅 — `~/.hermes`는 git 저장소가 아니라 훅을 걸 대상이 애매함.
- **내 의견**: (c). 크론은 `no_agent: true`로 돌려 토큰을 0으로 만들고, 실패할 때만 알림을 보낸다. PR 전 실행은 규칙이 아니라 PR 템플릿의 체크박스로 둔다.

## Q5. 강연의 "자동 머지"까지 갈 것인가

- **사실**: 내 PR 규칙은 "리뷰 없이 머지 금지"다. 강연의 자동 머지는 리뷰가 필요 없을 만큼 코드베이스와 게이트가 성숙했을 때의 이야기다.
- **내 의견**: 가지 않는다. 대신 "게이트 통과 + 리뷰 1회"를 유지하고, 리뷰에서 잡히는 결함이 줄어드는 것을 근거로만 재검토한다(4단계 조건).

## Q6. 코드에 남은 산문(주석) 정책

- **선택지**: (a) 새 레포에서만 주석 최소화 실험. (b) 기존 레포까지 소급. (c) 현행 유지.
- **내 의견**: (a). ASL·contest-mcp처럼 이미 리뷰 문화가 자리잡은 레포에 소급하면 소음만 생긴다. 새로 만드는 레포에서는 "주석 대신 테스트 이름과 게이트 메시지로 의도를 남긴다"를 기본으로 한다.

## Q9. 스킬 폴더를 pstack/gstack처럼 재편할 것인가 — **결정: 지금은 하지 않음** (2026-11-27 조사 고정)

아래 수치는 이 조사 시점의 측정값이다. 재편을 다시 열 때는 다시 재라.

- **폴더는 이미 있다.** `~/.hermes/skills` 자체가 pstack의 `skills/`에 해당하고, Hermes는
  카테고리 하위폴더 + 인덱스 헤더 렌더를 이미 지원한다(`prompt_builder`가 `category:` 헤더로 그림).
- **분포만 어긋나 있다**: 최상위 낱개 163개 vs 카테고리 안 114개. `security/`에 있어야 할
  `analyzing-*`류가 최상위에 흩어져 헤더 없이 나열된다.
- **토큰 이득은 거의 없다**: 최상위 낱개를 10개 카테고리로 묶으면 인덱스 +512자. 이득은
  비용이 아니라 **탐색성**이다(사람과 에이전트가 헤더로 위치를 본다).
- **진짜 구멍은 git이 없다는 것**: 내가 만든 스킬 167개·7.8MB가 저장소 밖에 있고, 복구 수단은
  `.curator_backups`(최근 5개, 65MB)뿐이다. pstack/gstack의 본질은 "클론하면 그게 스킬 폴더"다.
- **공개는 불가**: 활성 스킬 95개 파일에 서버 IP·내부 호스트가 박혀 있다(`158.180.x.x`, `10.x`).
  추적 레포를 만든다면 private 고정.
- **hub 설치 110개는 이동 대상이 아니다**: `archive_skill`이 거부하고 `hermes skills uninstall`은
  실제 삭제다.
- `Sahil-SS9-hermaguard`에 중첩 `.git`(원격 `Sahil-SS9/hermaguard`)이 있어 추적 시 서브모듈/제외 필요.

**선택지**: (a) 내 스킬만 추적하는 private git 레포를 먼저 만든다. (b) 최상위 낱개를 카테고리로
옮긴다. (c) 둘 다 — 레포를 만들고 정리 커밋을 그 위에 쌓는다(pstack 방식과 가장 유사). (d) 지금은 하지 않는다.

**결정**: (d). 게이트 작업을 먼저 끝내고, 폴더 정리는 위 측정값을 근거로 나중에 판단한다.
다시 열 때는 (c)를 기본으로 본다 — 순서는 "레포 생성 → 카테고리 이동 → 게이트 재실행 → 커밋".

## Q8. 자동 설치 보안 팩 770개를 인덱스에서 뺄 것인가 — **결정: (b) 실행 완료**

사용 기록 있는 19개와 hub 설치 78개는 그대로 뒀다 — 전자는 실제로 쓰이고, 후자는 `archive_skill`이
거부하며 `hermes skills uninstall`(실제 삭제)만 가능해 별도 승인이 필요하다.
결과: 인덱스 99,617 → **24,659자**, 활성 스킬 970 → 267개. 매니페스트:
`~/.hermes/state/slopgate/archive-manifest-*.json`, 복구 `hermes curator restore <name>`.
이어서 `SKL004`(아카이브된 스킬 참조) 전수 조사에서 사용 기록이 있는 10개를 복구해
최종 활성 **277개**·인덱스 **25,505자**·`.archive/` **822개**가 됐다(`docs/02-baseline.md`).

### 원래 검토 내용 (2026-11-26)

- **사실**: 스킬 988개 중 770개가 `mukul975/Anthropic-Cybersecurity-Skills` 팩(Apache-2.0)이다. 인덱스의 **81%**(≈20.5k 토큰/세션)를 차지하는데, 전체 세션 이력에서 **12번(9개 스킬)** 만 호출됐다. 반면 내 작업용 218개는 104개가 호출됐다.
- **선택지**: (a) `.archive/`로 전부 이동 — 인덱스 25.3k → **5.0k 토큰/세션**. 단 `.archive`는 `EXCLUDED_SKILL_DIRS`라 `skill_view`로도 조회 불가(되돌리려면 디렉터리를 다시 옮겨야 함). (b) 90일 내 사용된 9개만 남기고 761개 이동 — 사실상 (a)와 동일. (c) 그대로 두고 설명만 정리 — 절감 1~2k 토큰으로 미미. (d) 별도 `external_dirs`나 탭 재설치로 필요할 때만 되살린다.
- **내 의견**: (b). 쓰지 않는 761개가 세션마다 20k 토큰을 먹는 건 명백한 손실이고, 팩은 `taps.json`에 출처가 남아 있어 재설치가 가능하다. 다만 tae가 보안 실무 스킬을 "언젠가 쓸 카탈로그"로 의도한 거라면 (c)가 맞다 — 이건 취향이 아니라 사용 계획의 문제라 내가 정할 수 없다.
