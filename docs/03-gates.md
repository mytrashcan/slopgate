게이트는 세 종류이고, 각각 **적발 → 경고 → 차단**으로 승격할 수 있다.
지금은 모두 수동 실행이다. 언제 자동으로 돌릴지는 `docs/06-open-questions.md` Q4에서 정한다.

## 근사값이라는 사실 (SKL020 / SKL021)

인덱스 비용은 게이트가 **60자 하드 클립 + `...`** 로 근사한다. 실제 Hermes는
`agent/skill_utils.clip_skill_description()`으로 **단어 경계에서 자르고 꼬리 구두점을 지운다.**
실측(2026-11-27, 활성 277개): 게이트 25,505자 vs 실제 24,841자 — 게이트가 **+664자(2.7%) 과대**다.
방향이 안전(예산을 넘으면 실제로도 넘는다)하므로 근사를 유지한다. 정확한 값이 필요하면:

```bash
# ~/.hermes/hermes-agent 에서
$VENV/bin/python -c "from agent.skill_utils import extract_skill_description as f; ..."
```

`SKL021`(60자 안 트리거 없음)도 같은 근사를 쓴다. 단어 경계 절단은 더 일찍 자를 수 있어
실제로 트리거가 사라지는 스킬이 게이트 집계보다 조금 많을 수 있다.

## 오탐 위험 (중요)

게이트가 오탐을 내면 사람이 무시하기 시작하고, 무시되는 게이트는 없는 것과 같다. 그래서 아래를 명시한다.

- **SKL003**: 스킬이 `scripts/` 디렉터리를 안 갖고 있으면 그 참조는 "다른 저장소의 경로"로 보고 넘긴다. `*`·`<>` 플레이스홀더는 제외. `.archive/`는 기본 제외. 그래도 "프로젝트 레포의 `scripts/x.py`"를 스킬 안에서 가리키는 경우는 남을 수 있다 → 적발 시 스킬 문장을 고치는 것이 정답(어느 레포의 경로인지 명시).
- **SKL010**: 60자는 `skill_manage(create)` API 제약이고, 파일에 직접 쓴 설명은 길어도 동작한다. 120자 기준은 **비용** 기준이지 규칙 위반이 아니다. 그래서 경고에 머문다.
- **CRN010**: 데이터 수집형 크론은 후보 게이트가 없는 게 정상일 수 있다. `script`로 수집값을 주입하는 구조(수집이 결정론적)는 경고하지 않는다. 그래도 오탐이면 `--allow-unattended-agent`로 끈다.
- **SKL020/SKL021 계산 기준**: Hermes는 인덱스에서 설명을 **60자로 자른다**(`agent/skill_utils.py: SKILL_PROMPT_DESC_LIMIT`). 그래서 비용은 원본 설명 길이가 아니라 **잘린 길이**로 세야 한다. 원본 설명은 `raw_desc_chars`로 따로 보고한다. 이걸 모르고 원본 기준으로 예산을 잡으면 3배 과대평가한다(실측 295,194 vs 97,590자).
- **frontmatter 파서는 두 경로다**: PyYAML이 있으면 `yaml.safe_load`, 없으면 자체 파서. 두 경로의 측정값이 어긋나면 같은 트리도 환경마다 다른 판정이 나온다(CI 러너에서 `>-` 접기를 2자로 읽어 659개 스킬이 112,796자 누락된 사례). 자체 테스트가 `run_gate_no_yaml`로 **양쪽을 다 돌려** 값을 대조한다 — 한쪽만 검증하면 다른 쪽은 조용히 틀린다. `summary.parser`(`yaml`/`fallback`)로 어느 경로가 수치를 냈는지 확인할 수 있다. 남은 알려진 차이는 YAML 타입 강제(`yes`→`True`)뿐이고 판정에는 영향이 없다.
- **SKL021 은 파일별로 찍지 않는다**: 855줄이 쏟아져 요약이 묻힌다. 집계 1줄 + 예시 3개만 낸다(`--json`에는 전체 목록).
- **SKL022 는 '설명 문장이 비슷한가'를 보지 않는다.** 에이전트가 실제로 보는 것은 인덱스의 **앞 60자**뿐이므로 그 문자열로 판정한다. 두 축을 함께 본다 — ① 앞 60자의 내용어 겹침(작은 쪽 기준) ② 이름에서 선행 동사(`analyzing-`·`building-` …)와 일반어(`windows`·`files`·`python` …)를 뗀 주제어 겹침. 이름만 보면 `analyzing-*` 43쌍이 쏟아지고, 설명만 보면 도구만 다른 쌍이 걸린다.
- **SKL022 의 해법은 삭제가 아니라 앞머리 구분이다.** `PECmd-based: …` / `windowsprefetch library: …` 처럼 첫 단어에서 갈리면 에이전트가 고를 수 있으므로 보고하지 않는다. 이 예외가 없으면 설명을 실제로 고쳐 놓고도 게이트가 계속 울려서 결국 무시된다(그래서 테스트가 '앞머리를 구분하면 통과'를 함께 확인한다).
- **SKL022 예외는 `reason` 이 있는 항목만 인정한다**(`--overlap-allow`). 이유 없는 예외는 다음 세션이 "왜 둘 다 있지"를 다시 묻는다. hub 설치 스킬은 설명을 고치면 `hermes skills update`가 되돌리므로, 그때는 예외 목록에 이유를 적는 쪽이 맞다.
- **SKL023 은 '펜스 안의 `## `' 를 잡는 게 아니다.** 펜스 안 헤딩은 정상이다(템플릿 예시). 잡는 것은 **짝이 안 맞는 펜스**다 — 홀수면 그 뒤가 전부 코드로 렌더돼 본문이 화면에서 사라진다. 글자는 파일에 다 있으므로 `grep`·`split`·다른 게이트 어느 것도 울리지 않는다. 실제로 분할 도구가 펜스 안 `## `를 절 경계로 착각해 이 모양을 만들었고(`## Contribution (one sentence)` 같은 템플릿 줄이 절로 승격), SKILL.md 펜스가 11개(홀수)가 됐다. 그래서 (a) 분할 도구는 펜스 인식 파서로 바꾸고 (b) 결과의 펜스 짝을 검증하며 (c) 이 게이트로 상시 검사한다.
- **MEM004**: 400자는 임의 기준. 실제로는 "절차가 메모리에 있는가"가 기준이어야 하는데 그건 판단이라 게이트가 아니다. 길이는 **신호**로만 쓴다.
- **DAT001**: 날짜를 **문자열 리터럴 전체가 날짜일 때만**(압축형) 또는 `-`/`/` 구분자일 때만 인정한다. `2026.12.31`(버전), 맨 정수(`PORT=20261231`), 긴 hex/UUID 조각, URL 쿼리의 날짜는 제외 — 이 4가지는 실제 오탐이었다. 주석 줄은 건너뛴다. `--all-files` 없이는 테스트 경로만 본다. 그래도 API 응답 픽스처의 날짜가 진짜 미래 의도인 경우 오탐이 날 수 있다 → `--allow-file`로 개별 제외.
- **DAT001 은 '앞으로 도래하는 날짜'만 위반이다**(2026-11-28 정정). 처음에는 `--since` 기본값을 "오늘−90일"로 두고 그 사이 구간도 위반으로 잡았는데, **과거 날짜는 앞으로도 계속 과거**라 시간이 지나서 조용히 깨질 수가 없다. 실측: contest-mcp 158건 중 136건이 이미 지난 날짜였고, 그 136건이 진짜 폭탄 22건을 덮고 있었다. 지금은 기본이 "오늘"이고, `--since DATE` 를 주면 그 날짜 이후(과거 포함)를 위반으로 보는 **감사 모드**가 된다(만료된 픽스처 찾기). `--today DATE` 로 기준일을 고정해 테스트가 시계에 의존하지 않게 한다.
- **DAT001 의 경로 판정은 경로 조각 단위다**(2026-11-28 정정). 이전에는 부분문자열 매칭이라 `con`**`test_`**`mcp/src/contest_mcp/util.py` 가 테스트 파일로 분류돼 소스가 검사 대상이 됐다(오탐 2건). 지금은 디렉터리 조각이 `test(s)/spec(s)/__tests__` 이거나 파일명이 테스트 규약(`test_*`, `*_test.*`, `*.test.*`, `conftest*`)일 때만 테스트로 본다.
- **DAT001 은 점 구분·한국어 날짜도 날짜로 본다**(2026-11-28 정정). 이전에는 `2026.12.31` 을 "버전 문자열이 흔하다"는 이유로 통째로 제외했다. 그런데 이 저장소 계열 프로젝트(contest-mcp 등)의 테스트 픽스처는 **점 구분이 기본**이라 진짜 폭탄이 전부 미검출이었다(실측 7건). 지금은 `2026.12.20` 과 `2027년 3월 15일` 을 모두 잡는다. CalVer 오탐은 왼쪽 식별자로 가른다 — `VERSION = "2026.12.31"`, `APP_VERSION = "2030.1.1"` 은 통과, `DEADLINE = "2027.03.15"` 는 위반. `1.2.3`(semver)·`2026.12.31.1`(4절)은 정규식 경계로 제외.
- **리터럴 스캔(DAT001)은 'BASE를 고정 주입한 테스트'에서 오탐이다.** contest-mcp는 `BASE = date(2026,11,12)`를 모든 테스트에 주입하므로 픽스처 날짜가 미래여도 절대 안 깨진다 — 22건 중 실제로 깨지는 건 **1건**이었고, 그 1건은 픽스처가 아니라 `parse_period()`가 꼬리 연도를 `today()`에서 가져오는 **진짜 버그**였다(2030년에 `2026.12.20~01.05`가 2027-01-05가 아니라 2030-01-05로 파싱됨). 그 저장소에 필요한 게이트는 리터럴 스캔이 아니라 **시간 이동 실행**이다: `TIMEWARP_YEAR=2035 pytest -p timewarp_plugin` 처럼 시계를 미래로 돌려 스위트를 그대로 돌린다. 정적 스캔은 싸고 빠르지만 '오늘에 의존하는가'라는 실제 질문에는 행동 검사가 정확하다 — 둘은 대체가 아니라 층이다.

## 정적 게이트 vs 런타임 게이트

피라미드의 두 번째 층(정적 분석)과 세 번째 층(검증)은 다른 질문을 한다.

- **정적**(SKL/MEM/CRN/DAT): "설정과 파일이 규칙에 맞는가" — 파일만 읽는다. 빠르고 결정론적이다.
- **런타임**(RT): "자동화가 **실제로 돌았는가**" — 실행 기록(`last_status`·`failure_streak`·`next_run_at`·`last_delivery_error`)을 읽는다.

정적 게이트만 있으면 **조용한 실패를 못 본다.** 실제로 `SI-Weekly-Memory-Cron-Check`가 928초 모델
타임아웃으로 두 번 연속 실패하고 98시간 동안 방치됐는데, 설정 기반 검사는 전부 "정상"이었다.
RT001이 그걸 잡았고, 원인은 판단(메모리 정리·교훈 작성)과 수집(`hermes cron list`·메모리 전문·세션
검색)을 한 세션에 몰아넣은 것이었다 → 수집을 `~/.hermes/scripts/weekly-digest.py`로 분리해
크론의 `script`로 주입하고, 에이전트는 판단만 하도록 바꿨다.

## 자동 실행

게이트는 손으로 돌리면 잊힌다. 그래서 두 곳에 건다.

1. **일일 크론** (`slopgate 일일 위생 게이트`, `no_agent`, 매일 09:00, 토큰 0)
   - 스크립트: `~/.hermes/scripts/slopgate-daily.py`
   - 상태: `~/.hermes/state/slopgate/last.json` (이전 실행의 위반 목록)
   - **침묵 규칙**: 통과하면 아무것도 출력하지 않고, 실패해도 **새 위반이 없으면 침묵**한다. 첫 실행만 전체를 보여준다. 경고 피로를 만들면 게이트가 무시되기 때문.
   - `no_agent` 규약상 **항상 exit 0**으로 끝난다(위반은 stdout으로만). exit != 0 은 "스크립트 고장" 알림이 되어 매일 오탐 알림이 된다.
2. **CI** (`.github/workflows/gates.yml`) — `tests/test_gates.py`(게이트 자체 테스트)와 이 레포 대상 `date_bomb`.

프로젝트 레포(contest-mcp, OpenStreamGrid 등)의 날짜 부채는 일일 크론에 넣지 않았다. 기존 부채 164건을 매일 알리면 소음이고, 날짜 폭탄의 제자리는 **그 레포의 CI**(PR 시점)다. 필요하면 `slopgate-daily.py --repos <경로>`로 수동 점검한다.

## 게이트 자체 테스트

게이트가 조용히 고장 나면(정규식 오타 등) 아무것도 잡지 못하는데 겉으로는 "통과"로 보인다. 그래서 `tests/test_gates.py`가 각 게이트에 대해 **일부러 위반을 만들어 잡히는지**와 **오탐 입력이 통과하는지**를 함께 확인한다. 체크 개수는 실행 요약(`통과 N/N`)이 유일한 출처다 — 문서에 숫자를 적으면 게이트를 추가할 때마다 반드시 낡는다(`DOC001`이 이걸 검사한다).

```bash
/usr/local/bin/python3 tests/test_gates.py     # 마지막 줄의 '통과 N/N' 이 체크 개수
bash gates/run_all.sh --self-test              # 게이트 + 자체 테스트
```

## 실패 시 행동

게이트가 빨간색일 때 에이전트가 할 일:

1. 실패 항목을 고친다. 게이트 기준을 낮추는 것은 마지막 수단이고, 낮췄으면 이유를 커밋 메시지에 남긴다.
2. 고칠 수 없는 항목은 `docs/03-gates.md`의 오탐 위험에 근거를 적고 allowlist에 넣는다.
3. 게이트 자체가 틀렸으면 게이트를 고친다. 게이트 코드도 리뷰 대상이다.

## 새 게이트를 추가하는 절차

1. `templates/correction-to-gate.md`로 "왜 산문이 아니라 검사인가"를 먼저 적는다.
2. `templates/gate-spec.md`로 명세를 쓴다 (ID, 검사 대상, 오탐 위험, 승격 조건).
3. `gates/`에 코드를 넣고 **일부러 깨뜨려서** 잡히는지 확인한다.
4. `gates/run_all.sh`에 연결한다.
5. 이 문서의 표에 한 줄 추가한다.
