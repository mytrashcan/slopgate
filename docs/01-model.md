# 모델 — 코드 레포의 원칙을 Hermes 운영으로 옮기기

강연은 "코드 레포 + 코딩 에이전트"를 전제한다. 내 Hermes는 레포가 아니라 **운영체제에 가까운 산문 덩어리**다.
그래서 층을 그대로 복사하지 않고, 각 층의 **대응물**을 정한다.

## 5계층 대응표 (강연의 실제 명칭 기준)

강연 슬라이드의 다섯 칸은 위에서부터 **코드베이스 · 정적 분석 · 검증 · 산문 · 사람 리뷰**다. 위가 넓고 아래가 좁다.

| 층 (강연 명칭) | 강연 (코드 레포) | Hermes 대응물 | 현재 상태 |
|---|---|---|---|
| 1. 코드베이스 | 모듈 경계, 디렉터리 규약, API 설계 | 스킬 디렉터리 구조(`references/`·`scripts/` 분리), 크론=스크립트+게이트 형태, `~/.hermes/scripts/` 단일 실행 지점 | 부분적. 스크립트는 있으나 규약이 문서에만 있음 |
| 2. 정적 분석 | eslint, tsc, 의존성 분석기 | `gates/*.py` — 스킬 frontmatter·참조 실존·인덱스 예산·메모리 예산·크론 프롬프트 길이 | **이 저장소에서 시작** |
| 3. 검증 (런타임) | DevTools, feature map, 실제 앱 클릭 | 도구 출력 그라운딩, 외부 쓰기 read-back, 게이트 실행 증거, 후보 게이트(monitor_script) | 습관으로는 있음(메모리 규칙). 검사로는 없음 |
| 3. 검증 (형식) | TLA+, Lean, 속성 기반 테스트 | **미도입** (아래 이유) | 없음 |
| 4. 산문 | AGENTS.md, 스킬, 규칙 | `AGENTS.md`, 스킬 968개, 메모리 57항목 | 과다. 인덱스만 30k 토큰/세션 |
| 5. 사람 리뷰 (가장 좁은 칸) | 코드가 아니라 검증 산출물(영상·스크린샷·다이어그램)을 본다 | PR 리뷰 = 게이트 출력·실행 로그 확인, 코드 재독은 그다음 | 혼합. 코드 재독 비중이 큼 |

목표는 리뷰를 없애는 게 아니라 **리뷰가 보는 것을 바꾸는 것**이다. 리뷰가 매번 같은 실수를 잡고 있다면
그건 사람의 부주의가 아니라 1~3층이 비어 있다는 신호다. 그래서 이 저장소의 작업 순서도 1층 → 2층 → 3층이다.

### 형식 검증을 도입하지 않는 이유

강연의 팀은 Electron 클라이언트를 수천 PR/월로 굴린다. TLA+는 "여러 기기·플랫폼에 걸친 알림" 같은
동시성 흐름에서 값을 냈다. 내 Hermes에 그런 흐름은 없다. 있는 것은 파일 시스템 조작, 외부 API 호출,
크론 스케줄이다. 이 영역에서 형식 검증보다 싸게 같은 목적(속성이 깨졌는지 확인)을 달성하는 수단은
**게이트 + 속성 테스트**다. 나중에 동시성 있는 서비스(예: 릴레이 동기화)를 만들면 그때 ASL 레포 쪽에서 검토한다.

## "교정 → 결정론" 변환 사례

산문에만 있던 규칙을 실제 검사로 옮긴 것과, 아직 산문인 것을 구분한다.

| 실수/교정 | 어떻게 막고 있나 | 상태 |
|---|---|---|
| 크론이 후보 없이 30분마다 실행 → 483회·8,670만 토큰 소모 | `monitor_script` 게이트(`hermes-sweeper-gate.py`)로 후보가 있을 때만 모델 기동 | 완료 (코드) |
| 크론 프롬프트가 9.5k자를 넘어 `cronjob` update 실패 | `CRN001` 길이 검사 | **신규 (이 저장소)** |
| 상시 메모리가 97%로 차서 새 사실이 기존 항목을 밀어냄 | `MEM003` 예산 검사 | **신규** |
| 스킬이 없는 `references/x.md`를 가리켜 에이전트가 헛걸음 | `SKL003` 참조 실존 검사 (현재 12건 적발) | **신규** |
| 스킬 인덱스가 커져 매 세션 30k 토큰 소모 | `SKL020` 인덱스 예산 (경고) | 신규, 예산 미확정 |
| 테스트 픽스처에 가까운 미래 날짜 → 만료 후 CI 실패 | 스킬 산문 + 메모리 항목 | **아직 산문** → 날짜 린트 백로그 |
| PR 생성 전 승인 필요, 리뷰 없는 머지 금지 | 메모리 규칙 + 리뷰 게이트 운영 | 부분적. 게이트로 만들 수 있는 부분은 `gh pr view --json reviewDecision` 검사 |

## 이 저장소가 지키는 규칙

1. 새 규칙은 **검사 우선**. `docs/03-gates.md`에 명세를 쓰고 `gates/`에 코드를 넣는다.
2. 검사로 만들 수 없는 것만 산문에 쓴다. 그때 `templates/correction-to-gate.md`에 "왜 검사가 아닌가"를 남긴다.
3. 게이트는 **오탐을 먼저 의심**한다. 오탐이 나는 게이트는 무시되기 시작하고, 그러면 없는 것과 같다.
4. 게이트 출력은 사람이 읽을 수 있어야 한다. 실패 메시지에 "무엇을 고쳐야 하는지"가 들어간다.
